# 电影 / YouTube 对白精炼流水线（设计定稿 v2）

从本地音视频提取「只剩对白、长停顿被压缩」的连续音频 + 双语 LRC，再复用现有
Echo Loop 链路产出 `_tnt` / `_tst` 学习音频。

本文是 v1 方案经过设计评审后的定稿。**「决策」小节记录的是已经拍板、不要再回退的选择**，
每条都附了当初为什么这么定。

### 分离模型：htdemucs

2026-08-26 用《搏击俱乐部》两段素材实测了四个方案，**选 htdemucs，理由是速度**。

| 方案 | 30 秒素材 | 30 分钟素材 | 显存峰值 | 分成几类 | 语音/空白落差 |
|---|---|---|---|---|---|
| **htdemucs** ✅ | ~10s | **约 110 秒** | 4.3 GB | 人声 / 伴奏 | +11.5 dB |
| htdemucs_ft | ~8s | 约 4 倍于上 | 类似 | 人声 / 伴奏 | +11.8 dB |
| BS-RoFormer | ~14s | — | — | 人声 / 伴奏 | +11.7 dB |
| TIGER-DnR | 46s | **约 46 分钟** | 2.1 GB | 对白/音乐/音效 | +12.0 dB |

**权衡**：TIGER 的对白轨确实更干净（打斗戏上听感差别明显，因为它是唯一有「音效」
这一类的模型 —— demucs 和 RoFormer 只有「人声 vs 伴奏」两个桶，拳头声无处可放会漏进人声轨）。
但它慢于实时，一部电影约 3 小时，而 htdemucs 只要 5 分钟。

**决定按速度选 htdemucs**，因为下游剪辑真正需要的是「语音段 vs 空白段」的电平落差，
两者分别是 +11.5 dB 和 +12.0 dB —— 都够 VAD 用，差距只有 0.5 dB。
（对照：**原混音只有 −1.2 dB**，空白处和语音段平均能量相当。

注意别把这条读过头：silero 是神经网络模型不是电平门限，在原混音上照样找得到语音。
实测同一段 30 秒素材，原混音 VAD 找到 6 段共 8.1 秒，人声轨找到 5 段共 9.9 秒
（真实约 11 秒）。分离带来的是三个具体改善：撞击声不再被误判成语音、连续说话
不再被切碎、漏检更少 —— 是改善不是从零到一。

**分离真正不可替代的地方是产物本身**：`*_dialogue.mp3` 要的就是「没有背景音乐的
对白」，这是功能定义。剪辑质量的提升是附带的。）

TIGER 保留为**已验证的升级路径**：如果将来对听感产物要求提高、且能接受过夜批处理，
换过去只需替换分离这一步，下游不用改。踩坑记录见下。


### 已知代价：动漫的 OP/ED 歌声会留在对白轨

2026-08-29 用《命运石之门 剧场版》实测：片头曲那 134 秒里，**81.5 秒（61%）被当成
对白保留了下来**。

原因在 demucs 的分类方式，不是 bug：它只分「人声 vs 伴奏」，而唱歌就是人声。
分离后的 vocals 轨里有歌声 → VAD 在那条轨上判定「有人在说话」→ 剪辑保留。

**这条已经评估过并接受了**，不要再去查：

- 真人电影影响小（配乐通常是器乐）
- 动漫每部大概几分钟（OP + ED + 插入曲）
- 剪辑后是连续对白，听到一段歌跳过即可

想彻底解决只有换 TIGER-DnR —— 它有独立的「音乐」类别，唱歌会进音乐轨。
代价是一部片子从 4 分钟变成 3 小时。取舍见上面的分离模型对比表。

**别为这个往流水线里加机械修补。** 曾经试过两条弯路，都被推翻了：

1. 「按汉字相邻检测断词」—— 日语句尾句首本来就常是汉字，误报泛滥，
   而真正的平假名断词（な|ぜ）它看不见
2. 「修复跨越巨大静音的词时间戳」—— 那个「异常间隙」本身就是被保留的歌声，
   修的是错误诊断的症状

教训：拿到现象先验证原因，别假设一个就动手修。上面那 81.5 秒只用一条命令就能量出来，
却是在写了两百行修补代码之后才去量的。

**别再评估 SAM-Audio**：依赖地狱（`huggingface_hub>=1.0` 不兼容 → 降级后撞
`transformers 5.x` → 再降后卡在 ImageBind），且 8GB 显存只够跑 `sam-audio-small`，
拿不到 `base` 的质量优势。权重 7.2GB。

## 1. 阶段顺序（决策）

```
本地 ffmpeg 抽音频（复用 extract_audio.py，含 10 分钟分段）
  → 上传音频（不是 mp4）
  → [GPU] htdemucs 分离出人声 stem      ← 长音频必须先切 15 分钟一段
  → [GPU] Whisper 转写 stem             ← 拿文本 + 词序 + 粗略时间
  → [CPU] 在同一条 stem 上跑 VAD        ← 拿真实语音边界
  → 按 VAD 边界剪辑 + 生成时间映射
  → 词时间戳过映射函数 → LLM 分句 → 翻译
  → Echo Loop
```


### 决策 1.0：哪一步在哪台机器上跑

> **GPU 机只做需要 GPU 的两件事：人声分离、whisper 转写。其余全部在 Mac。**

```
Mac  ──原音──────────▶  GPU 机 : htdemucs 分离
Mac  ◀────────stem────  GPU 机
Mac  : VAD 找边界 → 剪辑                      ← 剪辑必须在转写之前
Mac  ──剪辑后的音频────▶  GPU 机 : whisper 转写
Mac  ◀────result.json──  GPU 机
Mac  : 切块 → 分句 → 翻译 → Echo → 同步
```

理由（三条，按重要性）：

1. **剪辑那几步根本不需要 GPU** —— VAD 用的 silero 是 1MB 级的 CPU 模型，
   剪辑是 pydub/ffmpeg 的纯 I/O，电平判定是 numpy 上的滚动最小值。
2. **产物的归宿在 Mac** —— 剪辑输出直接喂给 `main.py --scan`，而 Echo 的 config、
   Google TTS 凭据、iCloud 同步全在 Mac 上。放 GPU 机就是绕一圈再传回来。
3. **避免环境双份** —— `tools/dialogue_cut.py` 依赖 Mac 上 `echo_env` 的
   faster-whisper 和 pydub。在两台机器各维护一份，正是 `~/.config/echo/paths.env`
   那个教训的复现方式（路径复制进 4 个脚本，迁移时漏改 3 个，静默失效很久）。

附带好处：那台笔记本会关机（实测断过），而只要几十秒的步骤不该依赖一台可能没开的机器。

**代价：变成两次往返。** 转写排到剪辑之后（决策 1.1），所以音频要上去两趟。传输量反而
小了（第二趟传的是剪掉静音之后的音频），但流程上多一次等待，而且**中间那台机器不能关**。


**分离输出建议加 `--flac`**：无损，体积减半（30 分钟 303MB → 150MB）。
局域网上只省几秒，整片处理时省约 600MB 和半分钟传输。ffmpeg/pydub 原生读 flac，
下游无感。属于顺手不亏，不是性能优化。

### 决策 1.1：转写分离后的 stem（2026-08-30 实测改定，原为转写原音）

原文写的是「转写原音」，理由是「large-v3 对背景配乐的鲁棒性，通常好过对分离伪影的
鲁棒性；stem 的 artifact 会直接变成 WER 和时间戳误差」。**这条理由从来没有实测支撑，
2026-08-30 补测后不成立。**

测法：《搏击俱乐部》取 6 段各 6 分钟（全片均匀取样，合计 36 分钟），参照物是 mkv 内封的
人工英文字幕流。同一段素材分别转写原混音和 htdemucs 的 vocals stem，同一个 whisper 服务、
同一套参数。

| 指标 | 原混音 | vocals stem |
|---|---|---|
| 词错误率 | 24.23% | 24.71% |
| 句首词时间戳误差（绝对值中位数） | 150 ms | 190 ms |
| 落在无语音区间的词（幻听） | 5.17% | 4.37% |

差 +0.48 个百分点；按字幕行做 8000 次 bootstrap 重采样，95% 区间 [−1.25, +2.35]，含 0；
逐行胜负 69:64，符号检验 p = 1.0。**两者没有可测量的质量差别。**

> 方法论上的坑，值得单独记一笔：只用前 2 段素材时，结论是「stem 好 2.51 个百分点，
> 95% 区间 [−4.87, −0.14] 不含 0，方向稳健」。补到 6 段后这个结论完全消失。
> 素材量不够时，bootstrap 照样会给出「稳健」的假象。

既然质量上没差别，就按流水线本身的需要选：**转写 stem**。收益是 whisper 的词时间戳和
剪辑用的 VAD 落在同一条信号上 —— `dialogue_cut.py` 里「VAD 区间 ∪ whisper 词区间」那个
并集不再是跨两种信号的拼接。

**代价（已知并接受）：**

- **分离从「可降级」变成硬依赖。** 原来分离失败还剩一份完整字幕，现在整条任务作废。
  gpu-box.md 第 ⑥ 条那个 OOM（90 分钟音频吃超 10.3GB 被内核杀掉）现在会连带干掉转写，
  所以「长音频切 15 分钟一段」从建议升级为**必须**。
- **分离偶尔会把一段话搅坏。** 36 分钟里出现 1 次：影片 31:20 附近，stem 把
  "The things you own end up owning you / My insurance is probably gonna cover it"
  转成了 "can you owner of these scooters / you are the B gamb Serking woman"，
  原混音那一段是对的。反方向的例子也有（另一段 stem 比原混音好 3.18 个百分点）。
  两边都会局部翻车，不是系统性偏向 —— 这也正是总体没有差异的原因。

### 决策 1.2：本地抽音频，别把 mp4 传上去

`create_job` 里的 `shutil.copyfileobj` 是同步调用写在 async 端点里，传 2GB 会卡死
事件循环，连带把并发任务的 SSE 一起停掉。本地 ffmpeg 抽完再传，顺便省掉 Windows 侧
的解封装。

`extract_audio.py` 默认 `--split-threshold 600 --chunk-duration 600`，长素材本来就会
切成 10 分钟段——dialogue 入口**复用它**，按段进流水线。一部 2 小时电影整片当一个 job，
Echo 产物会是 6 小时以上的音频，实际不可听。

## 2. 边界从哪来（决策）

### 决策 2.1：边界用 VAD，文本和顺序用 ASR

Whisper 的词级时间戳是从注意力权重对齐推出来的，误差量级 100~200ms。用它决定剪刀落点，
等于拿一把误差 ±150ms 的尺子做 150ms 的精细活。

**方向的实测修正（2026-08-30）**：原文写「词首系统性偏晚」，这是错的。用上面同一批 6 段
素材，参照物是在干净 stem 上量出的声学起点（音量从静音跃起的那一刻）：

| | 原混音 | stem |
|---|---|---|
| 中位数 | 偏**早** 70 ms | 偏**早** 150 ms |
| 绝对误差中位数 | 150 ms | 190 ms |
| 晚于声学起点的比例 | 28.3% | 25.4% |
| 晚超过 100 ms 的比例 | 11.5% | 13.0% |

误差量级 100~200ms 这条成立，但**方向是两边都有、总体偏早**。这一点很重要，因为两个
方向坏在不同的地方：偏晚切掉这一句的词头，偏早切掉上一句的词尾。结论不变 —— 词时间戳
不能用来决定剪刀落点。

所以：**在分离后的 stem 上单独跑一次 VAD 拿边界**（背景音乐已经没了，VAD 在这里特别准，
这是分离这一步顺带送的红利），whisper 只负责「说了什么、什么顺序」。

### 决策 2.2：剪辑 VAD 必须是独立的一次运行，参数和转写 VAD 不同

**这是最容易踩的坑。** 现有服务转写时已经在用 VAD（`server_general_lrc.py:812`）：

```python
vad_parameters=dict(min_silence_duration_ms=700, speech_pad_ms=300, threshold=0.35)
```

这套参数是为「不要把句子切碎」调的，直接拿它的输出去剪辑会同时踩两个雷：

| 参数 | faster-whisper 默认 | 现有转写用 | 剪辑必须用 | 为什么 |
|---|---|---|---|---|
| `speech_pad_ms` | 400 | 300 | **0** | VAD 自己已经加了 padding，再叠加自己的 150ms 就是双重 padding |
| `min_silence_duration_ms` | 2000 | 700 | **200** | 高于这个值的静音才算边界。用 700 的话，短停顿根本不会成为语音段的分界，整段话连成一片，剪辑规则无从下刀 |
| `threshold` | 0.5 | 0.35 | 0.35 | 沿用现有调校 |

padding 只能有一个来源。`speech_pad_ms=0` 之后，留量完全由第 3 节的规则显式控制 —— 而那条规则
现在是逐段量出来的，不是常数（见决策 3.1）。

## 3. 剪辑规则（决策）

### 决策 3.1：刀口落在验证过的底噪里，两边各留 30ms（2026-08-30 实测改定）

原文是「句间总间隔上限 600ms，两侧各留固定 300ms」。**那个 300 是拍出来的常数，实测撑不住。**

推翻它的测量（515 个语音段，干净人声轨，判据只比本地底噪高 6dB）：

| VAD 边界之外还有多少声音 | 中位 | p75 | p90 | p95 | 最大 |
|---|---|---|---|---|---|
| 起点之前 | 50ms | 110ms | 226ms | 323ms | 460ms |
| 终点之后 | 40ms | 150ms | 270ms | 350ms | 490ms |

**VAD 给出的边界落在声音内部，不是声音的边缘。** 零留量直接按 VAD 边界下刀会削掉
92.4% 的词头。这不是 VAD 的毛病 —— 清辅音本来就是从几乎无声慢慢爬上来的，任何阈值
都必然触发得晚。所以任何一个固定常数都同时犯两个错：对短促的句子多余，对慢起音的句子不够。

**新规则：不猜，逐段去量。**

```
对每个相邻语音段之间的空隙：
    从左边那段往右走到底噪  -> k
    从右边那段往左走到底噪  -> j
    k + 30ms < j - 30ms  ->  在中间下刀，两边各留 30ms
    否则                 ->  这一刀不剪，两段连着保留
```

- 「本地底噪」= 能量的 ±2 秒滚动最小值。用滚动值而不是全局阈值，是因为分离残留的底噪
  在整片里并不均匀，全局阈值在安静段过敏、在嘈杂段失效。
- 「有声音」= 高于本地底噪 6dB。
- 「到达底噪」要求**连续 50ms** 都在底噪上。单帧判定会被静音里的能量抖动一步骗过去 ——
  实测过，刀口会落在还有声音的地方。
- 片头片尾按同样规则处理。
- 接缝 5ms 淡入淡出。

**不变量（测试直接验这两条）**：
1. 每一刀都严格落在已连续 50ms 到达底噪的区间内部。
2. 每一段 VAD 语音都被完整保留，一帧不少。

**句间空白从 600ms 变成 60ms。** 原文说「300ms 的句间距听起来像被快进过，600ms 接近
正常对话换气」—— 那是把这条音频当成品听的假设。实际它是 Echo 的素材，Echo 会按字幕行
重新切段并自己插入间隔，所以这里的空白不需要承担听感职责。

**代价：压缩率下降，而且随素材而变。**

| 素材 | 旧规则 | 新规则 | 放弃下刀的边界 |
|---|---|---|---|
| 《搏击俱乐部》36 分钟 | 剪掉约 27% | 剪掉 23.3% | 221 / 622（36%） |
| 《命运石之门》6 分钟 | 剪掉 18.2% | 剪掉 11.5% | 87 / 138（63%） |

动漫那一段压缩率明显更低，**因为那段本来对白就密集，可剪的静音少**。这条已评估并接受：
目标是「没有空白」，不是「尽可能短」。不要为了压缩率去调松底噪判据 —— 那等于把削词头
重新买回来。

**剪掉静音会不会伤转写？实测不会。** 同样 6 段素材，转写剪辑前 vs 剪辑后：WER
24.71% → 23.29%，bootstrap 95% 区间 [−3.21, +0.14] 含 0；**词数几乎完全一致**
（4733 → 4710）—— 削掉词头的话这里会掉词。

### 决策 3.2：时间映射只用于审计，不再参与产出（2026-08-30 改）

决策 1.1 翻转后，转写跑在剪辑**之后**，词时间戳天然就在剪辑后的时间轴上。
**原来那套「所有词时间戳过映射函数」的重映射整步消失了**，`remap_whisper()` /
`remap_time()` 一并删除。

timeline JSON 仍然产出（每条记录 `source_start/end → output_start/end`），
但只用于审计和回溯源时间，下游不读它。

顺带删掉的还有「保留区间取 VAD 区间 ∪ whisper 词区间」那个并集。它当初是为了防
「字幕还在、音频却被剪掉」—— 新顺序下字幕来自剪辑后的音频，不可能引用不存在的音频，
这个失败模式从结构上消失了。剩下的风险变成「孤立短句被剪掉且无人知晓」，由上面那条
词数一致性兜底。

**仍然成立的一条**：VAD 语音区间和最终字幕行是对同一条时间轴的两种不同切分，不需要、
也不会一一对应。不存在「VAD 区间 = 字幕行」这个约束。

### 决策 3.4：Echo 的 target clip 起止时间都逐句从音频量（2026-08-30 实测定）

这条属于 Echo 阶段，不是剪辑阶段，但它和决策 3.1 是同一个道理的两次应用：
**边界要从音频量，不能用推出来的时间戳。**

LRC 每行只有开始时间，`parse_lrc` 只能把 `end_ms` 推成「下一行的开始时间」
（`parser/lrc_parser.py:265`）。照着这个值直接切，两端都出问题：**实测至少 10% 的
clip 两端一点留量都没有**（留白分布的 p10 = 0），那些就是切进词里的；反过来，
一句话后跟长停顿时整段停顿被算进 clip，尾部空转最长 3.43 秒，还和
`after_first_target: 0.8s` 叠加，停顿忽长忽短。

`audio/splitter.py` 现在逐句从音频量起止时间，两端对称：

- 边界落在语音里 → 往回退 / 往后走到这段语流的边缘（上限 `MAX_HEAD_EXTEND_MS`
  / `MAX_TAIL_EXTEND_MS` = 400ms；退不到就不动，那说明和邻句是连着说的）
- 边界落在静音里 → 收掉多余的空转
- 然后加 200ms 留量（`HEAD_PAD_MS` / `TAIL_PAD_MS`），但**留量只吃静音** ——
  碰到邻句的声音就停，绝不把邻句的片段带进来
- 判据是**相对**的：高于「附近 ±2 秒峰值 − 25dB」才算有声

`Segment` 上的时间戳一个字节不动（那是共享数据），只影响切片；输出 LRC 本来就按
clip 实际解码长度重建（`export/lrc_writer.py:69`），自动对齐。

实测（同一条音频、同一批 100 个 segment，唯一变量是切法）：

| | 头部留白 p10/中位/p90 | 尾部留白 p10/中位/p90 | 总时长 |
|---|---|---|---|
| 旧（照 LRC 切） | **0** / 135 / 410 ms | **0** / 50 / 895 ms | 436.1s |
| 头尾都修 | 18 / 200 / 280 ms | 69 / 200 / 261 ms | 421.3s |

100 个 clip 里 85 个的起点被修正（45 个往前退到静音、40 个收掉开头空转），
10 个因为和邻句连着说、退不到静音而保持不动。

> **量这件事的时候注意**：能量判据**分不出「这一行的词」和「下一句的词」**——
> 连着说的时候它们声学上本来就是一段连续的声音。所以「clip 开头/结尾是不是语音」
> 这类判据会把「刀口正好落在起音上」也算成切坏，而那恰恰是最好的结果。
> 站得住的是上面那张留白分布表，不是那类计数。这个坑我踩了三次。

**四条已验证走不通的路，别再试：**

1. **换成 SRT 格式**并不解锁这件事 —— `extract_segment` 本来就不必用 `end_ms`。
   而且若 SRT 的结束时间取自 whisper 的词 `end`，那是**更差**的：实测系统性偏早
   120ms，81% 的句尾会被切掉，最多早 700ms。
2. **无条件给每个 clip 加尾部留量** —— 只有约一半的行结尾真被切了，另一半会把
   下一句开头拖进来。必须逐句判断。
3. **无条件加前置留量** —— 会把上一个词的尾巴拖进来，实测指标从 34.9% 恶化到
   52%，whisper 首词识别率从 89% 掉到 73%。
4. **让留量无条件吃满 200ms** —— 邻句紧挨着时会把它的片段带进来。留量必须只吃静音。

**剩下的不是切法能解决的**：和邻句连着说的那些行，声学上就是一段连续的声音，
边界挪到哪里都在词里。那是分句位置的问题，不是切音频的问题。


### 决策 3.3：~~分块切点对齐到非语音区间~~（已作废，见下）

**这条整条作废。** 它写的是 SAM-Audio 的分块策略（25 秒一块、3 秒重叠、等功率淡化），
而 SAM 已经在 2026-08-26 被否掉了（见第 0 节）。htdemucs **自己内部分段**，不需要
调用方指定切点，也不存在那个「重叠 3 秒被处理两遍造成相位干涉」的问题。

现在唯一还存在的分块，是**内存约束下的 15 分钟切段**（gpu-box.md 第 ⑥ 条：90 分钟音频
会被内核 OOM 杀掉）。切段的操作要求见 gpu-box.md 第 ⑦ 条：按采样点用 `soundfile` 读写，
并断言各段采样点之和等于源采样点数 —— 别信 `ffmpeg -c copy` 的容器时长。

**决策 1.1 翻转后留下的一个待办**：原文用「先转写、再拿转写结果挑非语音切点」来避开接缝
伪影。现在转写在分离之后，切段时手上没有转写结果。目前是按固定 15 分钟硬切，接缝可能
落在一句话中间。还没量过这个接缝到底有多明显 —— **在量之前不要动它**。真要处理，
成本最低的做法是在原音上跑一遍 CPU 上的 silero VAD（1MB 模型，几秒钟）来挑切点，
不需要 GPU、也不需要转写。

## 4. GPU 资源管理（决策）

### 决策 4.1：锁必须覆盖两个阶段

现有 `transcription_lock` 只锁转写。两个 dialogue 任务的 SAM 阶段会并行跑 → OOM。
把它提升成覆盖「分离 + 转写」全过程的 GPU 锁。

### 决策 4.2：起分离模型之前必须显式释放 Whisper

`IDLE_RELEASE_SECONDS = 10 * 60`（`server_general_lrc.py:45`）——上一个转写任务结束后
Whisper 还会常驻 10 分钟。dialogue 任务进来时，分离模型加载的那一刻显存里很可能还躺着 Whisper。

v1 方案只写了「分离跑完释放再加载 Whisper」，反方向没覆盖。需要在起分离 worker 之前调用
`force_release`，并处理它在有 active job 时会 raise 的情况（等锁，别吞异常）。

分离模型跑在独立进程 / 独立 venv（`~/audio-sep`），进程退出即彻底释放显存。
注意 whisper 用的是 `int8_float16`，比 float16 省显存，但两者仍不能同时常驻 8GB。

## 5. 产物生命周期（决策）

「产物保留到一小时 retention 到期」这句话要同时改三个地方，否则不是当场被删就是永久泄漏：

1. `run_transcription` 的 finally **无条件** `shutil.rmtree` 掉 job 的 temp dir
   → dialogue 任务的产物会在任务结束那一刻消失。需要按 `task` 区分。
2. `job_cleaner` 只 `jobs.pop()`，不碰文件 → 改完第 1 条后，文件永远留在 TMPDIR。
   需要同时删目录。
3. `cleanup_stale_temp_dirs` 按 `transcribe_*` 前缀 + 6h 扫 → 新的 dialogue 目录
   要么沿用这个前缀约定，要么单独加一条。

下载走白名单文件端点。失败任务不返回半成品。

另：现在没有 `/jobs/{id}` 状态轮询端点，进度只存在于 SSE 流里，断线重连拿不回
`job.progress`。5 分钟播客无所谓，两小时的分离+转写任务值得补一个。

## 6. Python 版本（决策：不升级）

| 环境 | 版本 | 约束来源 |
|---|---|---|
| WSL2 GPU 机 | **3.12.3**（系统自带） | TIGER / demucs 都能跑；约束是 torch / ctranslate2 的 wheel 滞后，不要追新 |
| Docker 镜像 | **3.12-slim** | 保持不动，见下 |
| mac conda `echo_env` | **3.11.15** | 保持不动 |

不升 3.13/3.14 的硬理由：**pydub 依赖 stdlib 的 `audioop`，而 `audioop` 在 3.13 被移除了**
（PEP 594）。当前解释器已经在报警：

```
DeprecationWarning: 'audioop' is deprecated and slated for removal in Python 3.13
```

pydub 铺在整个音频层的 7 个文件里（`audio/splitter.py`、`assembler.py`、`tts_generator.py`、
`timing.py`、`export/exporter.py`、`lrc_writer.py` 和测试）。升到 3.13 音频核心当场起不来。
`audioop-lts` 能顶，但那是把项目最核心的一层架在补丁包上。

而收益接近于零：3.13 的 free-threading、3.14 的改进解决的是 CPU 上纯 Python 的瓶颈，
这条链路的时间花在 GPU 推理和 ffmpeg 上，GIL 一秒钟都不是瓶颈。

另外换 Docker 基础镜像意味着要重新拉镜像，而那台 VPS 连不上 Docker Hub（TLS timeout），
CI 是靠本地缓存的 `python:3.12-slim` 在 VPS 上自己构建的——换版本会直接触发那个已知失败路径。

**真正的工作项不是升 Python，是摆脱 pydub**（它已多年少维护，`audioop` 移除只是第一个信号）。
现在 pydub 决定了这个项目的 Python 上限。但那是独立的一件事，不要和对白功能捆在一起做。

## 7. 产物

输入 `movie.mp4`：

- `movie_dialogue.m4a` —— 只剩对白、长停顿压缩后的连续音频
- `movie_dialogue.lrc` —— 双语字幕（时间直接来自转写剪辑后音频的结果，不经重映射）
- `movie_dialogue.timeline.json` —— 源时间轴 → 精炼时间轴的映射，**仅供审计回溯，下游不读**
- `movie_dialogue_tnt.m4a/.lrc`、`movie_dialogue_tst.m4a/.lrc` —— 复用现有 Echo 链路

命名已核对：`.m4a` 在 `scanner.AUDIO_EXTENSIONS` 里，`_tnt` / `_tst` 在 `OUTPUT_SUFFIXES`
里（重扫不会把自己的产物当输入），`.timeline.json` 会被扫描器忽略。

Windows result JSON 增加 `task`、`source_duration`、`output_duration`、`artifacts`；
segments 就是剪辑后时间轴上的原始转写结果，不再有 remap 这一步。旧字段不变，旧客户端不受影响。

### 与 CLAUDE.md 时间轴契约的关系

LRC 时间在压缩后的时间轴上，Echo 阶段也从压缩后的音频切 target clip，两者同源一致。
全程没有任何按字数 / 语速估算的时间——边界来自 VAD 实测，长度来自解码后的真实音频。
`estimated` timing provenance 一律视为失败。

## 8. 测试计划

**单元**（`tests/test_dialogue_cut.py`，12 个，用「谱面串」构造输入，不依赖任何真实素材）

两条核心不变量，其余都是它们的推论：

1. **每一刀都落在已连续 50ms 到达本地底噪的区间内部** —— 把剪掉的区间翻出来，
   里面不许有任何有声帧
2. **每一段 VAD 语音都被完整保留** —— 一帧不少

推论：下刀时两边各留 30ms；静音差一帧（<50ms）就不下刀；片头片尾按同样规则；
输出时间轴单调、无空洞、无重叠；剪辑只能变短；常量必须能整除成帧。

**回归**：现有转写 API、LRC 分句、翻译、audio timing、Echo Loop 测试全部保持通过。

**GPU 集成样本**：对白叠配乐、纯音乐、对白加音效、多人连续说话。

**端到端验收**：全部产物可完整解码；LRC 与 target clips 一一对应；无 estimated timing；
人工 A/B 确认对白首尾未被切断、背景明显降低、剪接无爆音。

**已经跑过的验收（2026-08-30）**：《搏击俱乐部》6 段共 36 分钟，参照 mkv 内封人工英文字幕。
转写剪辑前 vs 剪辑后 WER 24.71% → 23.29%，bootstrap 95% 区间 [−3.21, +0.14] 含 0，
词数 4733 → 4710。《命运石之门》6 分钟人工试听通过。
